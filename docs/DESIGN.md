# dsh-done-check 设计（v0.1）

> 为 DSH 编码任务保存可执行的验收清单，让每条"已完成"都有检查结果，并在代码变化后提醒重新验收。

首版只做一条完整流程：**定义检查 → 执行 → 保存证据 → 识别过期**。

## 1. 边界

- "全部检查通过"只表示**约定的检查**通过，不表示需求完整实现。任何界面都不显示百分比或"完成度"。
- 首版不拦截 Agent 的"完成"回答，不自动生成测试，不用模型判定需求是否完成，不截图，不自动修复重试。
- 威胁模型：防止 Agent **随手**改写结论（自称测试通过、偷改检查命令、删掉失败项、伪造确认记录）。**不防**拥有不受限 shell 的恶意 Agent——它能改 DSH home 下的任何文件，也能改测试本身。README 必须写明这一点。
- 确认清单只是固定验收标准，**不等于授权执行其中的命令**（见第 8 节）。

## 2. 文件与存储

| 位置 | 内容 | 谁写 |
|---|---|---|
| `<项目>/done-check.yaml` | 验收清单（可提交进 git） | Agent 起草或用户手写 |
| `$DSH_HOME/done-check/<projectId>/state.json` | 清单确认记录与索引：每项最新完成的运行、最近一次被取消的尝试、保留的历史、执行中的认领 | 仅插件 |
| `…/runs/<runId>.json` | 每次运行或人工结论的独立记录，写入后不再修改 | 仅插件 |
| `…/logs/<runId>.log` | 完整输出（有上限） | 仅插件 |

`projectId` = 项目根目录真实路径（Windows 上转小写、统一分隔符）的 sha256 前 16 位。证据放在项目外：一是不会改变工作区指纹，二是限定在工作区内的文件工具够不到。

## 3. 验收清单格式（`done-check.yaml`）

```yaml
version: 1
task: 新增 CSV 导出功能
checks:
  - id: export-tests            # 小写字母/数字/连字符，清单内唯一
    name: 导出相关测试通过
    run: pnpm test -- export    # 与 manual 二选一
    timeout: 120                # 秒，默认 300，上限 1800
    cwd: .                      # 可选，相对项目根，不得越出
    watch: ["src/**", "test/**", "package.json", "pnpm-lock.yaml"]  # 可选，缺省 = 整个工作区
  - id: typecheck
    name: TypeScript 类型检查通过
    run: pnpm tsc --noEmit
  - id: zh-filename
    name: 中文文件名下载正常
    manual: true
    watch: ["src/export/**"]
```

- **定义哈希**（逐项）：对每项的 `{id, name, run, manual, timeout, cwd, watch}`（填好默认值、`watch` 排序去重后）做规范 JSON 再取 sha256。任何字段变化都算定义变化；`name` 对人工项就是验收标准本身，所以也计入。
- **结构哈希**（整份清单）：对 `{task, 排序后的检查 id 集合}` 取 sha256。增删检查项、修改任务描述都会改变它。
- **`watch` 是用户声明的范围**，不是自动分析出的依赖关系。写窄了，相关代码改了结果也不会过期，这是用户的选择；插件只保证不出现"永远不会过期"的空范围（第 4 节）。

## 4. 工作区指纹

1. 用 `git ls-files -co --exclude-standard` 列出**已跟踪文件 + 未跟踪且未被忽略的文件**（v0.1 要求项目是 git 仓库）。已跟踪文件即使匹配 `.gitignore` 也会被检测；只有"未跟踪且被忽略"的文件不参与。
2. 排除 `done-check.yaml`（它的变化走定义哈希和结构哈希）。
3. 只编码**实际存在**的普通文件和符号链接；工作区里已删除的已跟踪文件直接不出现，删除通过前后文件集合的差异来表达。目录（如子模块）跳过。
4. 按该项 `watch` 过滤（缺省不过滤），逐个读取**工作区当前内容**取 sha256。
5. 指纹 = 对排序后的 `path\0hash\n` 序列取 sha256。同时保存逐文件哈希表，用于说明"哪些文件变了"。
6. 除"文件不存在"外的任何读取错误都向上抛出，调用方显示"无法判定"，绝不用部分数据算指纹。

性质（全部有测试）：
- 只看内容，不看 HEAD：未提交的修改会使结果过期；提交本身（包括提交删除、提交重命名）不会。
- 改了再改回原样，结果恢复有效（仅限执行时稳定的结果，见第 5 节）。
- 未跟踪且被忽略的文件、`watch` 之外的文件不影响结果。
- **空匹配**：显式 `watch` 在确认或执行时匹配不到任何文件，直接报错，拒绝确认或执行；此前匹配到的文件后来全部被删除，属于正常过期。

## 5. 状态

### 5.1 清单级

| 结构状态 | 条件 | 表现 |
|---|---|---|
| 未确认 | 从未确认 | 汇总以"清单未确认；"开头 |
| 已确认 | 当前结构哈希 = 确认时的结构哈希 | 正常汇总 |
| 结构已变 | 不相等 | 汇总以"清单结构已变，待确认（新增 …；删除 x（上次失败）；任务描述已改）；"开头 |

结构变化时，未改动项的证据照常保留和显示，但汇总必须先说明结构变了，被删除的项连同其上次结论一起列出。删掉一个失败项不会让汇总悄悄变好看。

### 5.2 逐项

每项状态由纯函数 `deriveStatus` 计算，从不持久化"状态"本身。按顺序判定：

| 状态 | 显示 | 条件 |
|---|---|---|
| `running` | 执行中 | 有未过期的执行认领（期限 = 开始时间 + 超时 + 60 秒） |
| `unconfirmed` | 待确认清单 | 确认记录里没有该项 |
| `definition_changed` | 清单已改动 | 确认时的定义哈希 ≠ 当前定义哈希 |
| `not_run` / `awaiting_manual` | 未执行 / 待人工确认 | 没有完成的运行，或运行属于旧定义 |
| `unknown` | 无法判定 | 运行记录无法读取或格式不符；`state.json` 损坏（此时所有项都是 `unknown`，且拒绝任何写入）；当前工作区无法读取 |
| `unstable` | 执行不稳定（须重跑） | 执行前后工作区指纹不同，或执行期间该项定义被修改 |
| `stale` | 已过期 | 运行绑定的指纹 ≠ 当前指纹；同时展示上次结论和变化的文件 |
| `passed` / `failed` / `error` | 通过 / 失败 / 执行出错 | 退出码 0 或人工通过 / 非零退出码或人工不通过 / 超时、无法启动、执行器故障 |

- **两种"变了"要分开**：执行时稳定、之后代码才变化的结果是 `stale`，代码改回原样即可恢复；执行期间就发生变化的结果是 `unstable`，无法确定检查针对哪个版本运行，**改回文件也不能恢复**，只有重新执行一次稳定的运行才能替代它。常见原因是测试生成了未被忽略的快照或覆盖率文件，原因中会列出这些文件。
- 失败和出错的结果同样会过期：旧代码上的失败不代表当前代码失败。
- 汇总只给计数，例如"3 项验收中，2 项通过、1 项待人工确认"。

## 6. 证据

### 6.1 内容

- 自动运行：`runId`、定义哈希、执行前指纹（含逐文件哈希表）、开始与结束时间、耗时、退出码或信号、是否超时、执行器错误、执行器类型（如 `pwsh-local`）、stdout/stderr 末尾各 8 KB、完整日志引用、不稳定原因。
- 人工结论：结论、备注、时间、当时的指纹。
- 取消：记录为一次**尝试**（时间、耗时），不替换最近一次完成的结果；状态仍按上次完成的结果显示，并注明"最近一次执行已取消"。

来源说明：检查的命令和名称可能由 Agent 起草；**执行结果由执行通道产生，清单确认与人工结论只来自用户命令，其余元数据由插件采集**。插件不向 Agent 提供任何写入证据的接口（威胁模型的限制见第 1 节）。

### 6.2 容量

- 完整日志每次运行上限 1 MiB，超出时丢弃开头，保留末尾，并在文件首行写明原始字节数。
- 每项保留最近 20 次运行记录，更早的连同日志一起删除；最新结果永不删除。单项最坏约 20 MiB。

### 6.3 并发

- 所有状态更新都经过项目级锁：进程内串行，跨进程用锁目录（`mkdir` 原子创建，超过 2 分钟视为遗留锁，等待上限 15 秒）。两个会话同时执行检查，不会互相覆盖确认记录或索引。
- 开始执行前先在锁内认领该项；同一项已有未过期的认领时，拒绝再次执行。执行器故障时会清除认领，不留"执行中"的残影。
- 运行记录各自独立；索引只指向每项最新完成的那一条。

## 7. 与 DSH 的接缝

| 能力 | 用途 | 谁能触发 |
|---|---|---|
| `ctx.tools`：`done_check_draft` | 校验并写入 `done-check.yaml`，提示用户确认 | Agent |
| `ctx.tools`：`done_check_run` | 执行已确认的自动项（授权方式见第 8 节） | Agent |
| `ctx.tools`：`done_check_status` | 返回结构化状态与汇总 | Agent |
| `ctx.commands`：`/done-check` | 状态表（Markdown） | 用户 |
| `/done-check confirm` | 确认当前清单 | **仅用户** |
| `/done-check run [id…]` | 执行检查（两步，见第 8 节） | 用户 |
| `/done-check pass\|fail <id> [备注]` | 人工项结论 | **仅用户** |

信任锚：确认清单和人工结论只能通过用户命令完成，命令不经过模型。

## 8. 命令执行与权限

DSH 的执行和授权是两层：`ctx.shell` 执行器（`bash-local`、`bash-sandbox`、Windows 上的 `pwsh-local`、`pwsh-sandbox`）只负责运行命令；其中 `*-local` **不做任何隔离**，命令以 harness 进程的权限运行。逐次的允许/拒绝/询问策略属于工具调用的 `tools/pre-execute` 阶段，直接调用 `ctx.shell` 会绕过这一层。因此：

- **Agent 入口**（`done_check_run`）：每条检查命令都必须经过与 Agent 自己调用 `bash`/`pwsh` 工具**相同**的授权流程，让权限策略看到的是真实命令，而不只是 `done_check_run`。实现方式是通过工具注册表转发给已注册的 shell 工具。若目标 DSH 版本做不到这一点，`done_check_run` 就不执行命令，只返回"请用户运行 `/done-check run`"。**绝不降级为直接调用 `ctx.shell`。**
- **用户入口**（`/done-check run`）：第一步只列出将要执行的确切命令、工作目录和执行器类型，并给出一个短期令牌；用户再输入 `/done-check run <令牌>` 才执行。令牌绑定当时各项的定义哈希，期间清单若被改动则作废。用户亲自看过命令、亲自输入，才算授权。
- 确认清单从来不是执行授权。
- 命令由当前组合挂载的 shell 解释：POSIX 上通常是 bash，Windows 上是 PowerShell。为一种 shell 写的命令在另一种上可能失败，结果照实记录为失败或执行出错，证据中写明执行器类型。
- 兼容版本：在本机 DSH 0.1.5-rc.1 上开发；插件层完成并在 0.2.x 上核实后，再在 `package.json` 写入 `engines.dsh` 范围。工具转发 API 和命令接口以实际验证的版本为准。

## 9. 分层

```
src/core/      纯逻辑，不依赖 DSH：清单解析校验、定义/结构哈希、指纹、状态推导、汇总
src/store/     state.json、运行记录、日志的读写、上限、加锁
src/service.ts 四个操作：confirm / runChecks / decide / report；执行器由调用方注入
src/plugin/    DSH 胶水：注册工具与命令，实现第 8 节的两个执行入口
```

core、store、service 用 `node:test` 在真实 git 仓库上覆盖；plugin 层在真实 DSH profile 里用 `dsh plugin add` 手工验收。

## 10. v0.1 发布标准

1. 在一个真实项目里走完：确认清单 → 执行检查 → 查看证据 → 修改代码 → 看到结果过期 → 重新验收。
2. 测试集全部通过，至少包含以下反例：
   - 过期判定：改已跟踪文件、新增未跟踪文件、改未跟踪且被忽略的文件（不触发）、改匹配 `.gitignore` 的已跟踪文件（触发）、改 `watch` 外文件（不触发）、改回原样（恢复）、删除文件、提交删除和重命名（不触发）。
   - 清单：改某一项（仅该项变为"清单已改动"）、删除失败项和新增项、改任务描述（结构已变）、`watch` 空匹配（拒绝）。
   - 执行：执行期间改文件后又改回（仍为不稳定）、执行期间改定义（不稳定）、超时与执行器故障（执行出错）、取消（保留上次结果并注明）、执行中状态与重复执行被拒。
   - 证据：运行记录损坏、`state.json` 损坏、工作区无法读取（均为无法判定）、日志截断、历史裁剪、跨实例并发写不丢更新。
3. README 第一屏写明第 1 节的边界与威胁模型，以及 `*-local` 执行器不隔离。

## 11. 之后再说

Web 面板（v0.1 用 Markdown 状态表达成发布标准）、Agent 从需求起草更好的清单、"测试文件在确认后被改动"提示、非 git 项目、在明确的完成动作上加门禁。
